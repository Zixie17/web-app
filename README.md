# ⏱️ Система учёта рабочего времени сотрудников компании (TimeTracker Pro)

Небольшое, быстрое и надёжное веб-приложение для учёта рабочего времени сотрудников, разработанное с нуля на стеке **FastAPI (Python)**, **SQLite** и **Vanilla JS / CSS**.

Приложение решает все ключевые задачи учёта рабочего времени: добавление сотрудников, запуск и остановку таймеров с описанием задач, подсчёт суммарного отработанного времени за выбранный период и персистентное сохранение данных после перезапуска.

## 🌟 Функциональные возможности

- **Управление сотрудниками**: добавление сотрудников с указанием ФИО, должности и отдела. Валидация входных данных на сервере и клиенте.
- **Интерактивный таймер задач**: выбор сотрудника из списка, ввод описания задачи и запуск таймера.
- **Живой секундомер**: тикающий счётчик времени (`ЧЧ:ММ:СС`) в реальном времени на веб-странице для всех активных задач.
- **Защита от параллельного запуска**: один сотрудник не может одновременно запустить две задачи (система выдаёт понятное предупреждение со ссылкой на активную задачу).
- **Остановка таймера**: корректная фиксация времени завершения, вычисление продолжительности и сохранение записи в базу.
- **Гибкая аналитика и отчёты**:
  - Быстрые фильтры по периодам: *Сегодня*, *Вчера*, *Текущая неделя*, *Текущий месяц*, *Всё время*, а также выбор произвольного диапазона дат (`Дата начала` — `Дата окончания`).
  - Фильтрация по конкретному сотруднику или по всей компании.
  - Сводная таблица с суммарным временем каждого сотрудника и числом выполненных задач.
  - Детализированный хронологический журнал задач со временем начала, окончания и длительностью.
  - **Корректный Empty State**: информативное отображение при отсутствии записей за выбранный период.
- **Персистентность (Persistence)**: база данных SQLite сохраняет все данные между перезапусками сервера.
- **Вымышленные демонстрационные данные**: при первом запуске база автоматически инициализируется реалистичными вымышленными сотрудниками и задачами.

## 🛠️ Архитектура и стек технологий

```
web-app/
├── app/
│   ├── __init__.py          # Пакет приложения
│   ├── main.py              # Точка входа FastAPI, маршруты REST API, lifespan
│   ├── database.py          # Инициализация SQLite, схемы таблиц, сидирование
│   ├── models.py            # Pydantic-модели валидации данных
│   ├── crud.py              # Бизнес-логика, SQL-запросы, подсчёт времени
│   ├── static/
│   │   ├── css/
│   │   │   └── style.css    # Адаптивный современный интерфейс
│   │   └── js/
│   │       └── app.js       # Клиентская логика, живые таймеры, fetch API
│   └── templates/
│       └── index.html       # Шаблон главной страницы панели управления
├── tests/
│   ├── __init__.py
│   ├── conftest.py          # Pytest-фикстуры, изолированная БД в tempfile
│   └── test_app.py          # 14 автоматизированных тестов сценариев
├── start.bat                # Запуск в 1 клик (автоматически открывает браузер)
├── run.py                   # Скрипт быстрого запуска приложения
├── requirements.txt         # Зависимости проекта
├── timetracker.db           # Локальная база данных SQLite
└── README.md                # Полная документация проекта
```

- **Backend**: Python 3.13, [FastAPI](https://fastapi.tiangolo.com/), [Uvicorn](https://www.uvicorn.org/) (ASGI).
- **База данных**: SQLite3 (реляционные таблицы `employees` и `time_entries` с индексами и внешними ключами `ON DELETE CASCADE`).
- **Frontend**: Семантический HTML5, чистый современный CSS3 (переменные, flexbox, grid, анимации), нативный JavaScript ES6+ (Fetch API, live interval).
- **Тестирование**: [pytest](https://docs.pytest.org/), `TestClient` (Starlette/HTTPX).

## 🤖 Использованные ИИ-инструменты и модели

В процессе разработки данного веб-приложения применялась модель:
- **Gemini 3.8 Flash (High)** в среде агентной разработки **Google Antigravity**.

### Задачи, решённые с помощью ИИ:
1. **Проектирование архитектуры**: выбор легковесного и надежного стека без избыточных зависимостей (FastAPI + встроенный SQLite + нативный JS).
2. **Моделирование данных**: составление SQL-схемы таблиц с внешними ключами, индексами и безопасными типами данных для меток времени в формате ISO 8601.
3. **Генерация бизнес-логики и граничных проверок**: разработка механизма блокировки одновременных задач для одного сотрудника и корректного расчёта разницы времени в секундах.
4. **Разработка интерфейса (UI/UX)**: создание чистого дашборда с вкладками, живым секундомером, карточками метрик (KPI) и всплывающими toast-уведомлениями.
5. **Написание полного набора автотестов**: 14 модульных и интеграционных тестов с проверкой всех граничных условий (повторный запуск, пустые отчеты, персистентность).
6. **Анализ и устранение багов**: диагностика поведения открытых файловых дескрипторов SQLite в ОС Windows и лексикографического сравнения строк дат.

Время начала и окончания должно сохраняться в ISO 8601. Если база данных создается впервые, автоматически заполни её 4 вымышленными сотрудниками и несколькими завершенными задачами, чтобы приложение сразу выглядело живым."*

### Запрос 2: Проверка и блокировка повторного запуска таймера
> *"Напиши функцию `start_timer(employee_id, task_description)` для FastAPI/SQLite. Если у сотрудника уже есть активный таймер (запись, где `end_time IS NULL`), система должна выбрасывать ошибку валидации с подробным пояснением, содержащим название текущей незавершенной задачи. Добавь соответствующую проверку и в UI, чтобы блокировать повторные запросы."*

### Запрос 3: Расчёт периодов и обработка пустого отчёта

### Запрос 4: Живой секундомер на JavaScript
> *"Напиши функцию на чистом JavaScript для вкладки активных таймеров. Она должна каждую секунду обновлять отображаемое время на карточках задач, вычисляя разницу между `Date.now()` и серверным `start_time`, чтобы таймер не отставал при переключении вкладок браузера."*

### Запрос 5: Изоляция тестов в Pytest на Windows

## 🐛 Найденные ошибки и их исправление

В процессе проектирования, кодогенерации и тестирования были выявлены и исправлены следующие проблемы:

| № | Обнаруженная проблема | Причина возникновения | Как исправлено |
|---|------------------------|-----------------------|----------------|
| **1** | **Повторный запуск таймера при активной задаче** | При отправке повторного запроса без остановки предыдущего создавались дублирующие активные записи с `end_time = NULL`. | В `app/crud.py` добавлена строгая проверка `get_active_timer(conn, employee_id)`. При обнаружении активной задачи возвращается HTTP 400 с текстом: *«У сотрудника уже запущен таймер для задачи: «...». Завершите текущую задачу перед запуском новой.»* |
| **2** | **Блокировка файла SQLite в тестах на Windows (`WinError 32`)** | В фикстуре `pytest` метод `os.remove(path)` завершался ошибкой `PermissionError`, так как Windows блокирует файлы, если сборщик мусора Python ещё удерживает дескриптор соединения. | В `tests/conftest.py` добавлен принудительный вызов `gc.collect()` перед попыткой удаления и безопасный блок `try ... except OSError: pass`. |
| **3** | **Срез дат фильтра отчётов по границам дня** | Если пользователь выбирал период, например, с `2026-11-08` по `2026-11-08`, строковое сравнение в SQL `t.start_time <= '2026-11-08'` отсекало все задачи этого же дня, созданные после 00:00:00 (например, в 14:30). | В `app/crud.py` добавлена автонормализация: `start_date` дополняется до `T00:00:00`, а `end_date` — до `T23:59:59.999999`. Задачи за весь выбранный день теперь попадают в отчёт корректно. |
| **4** | **Падение отчёта при отсутствии записей (Empty Report)** | При отсутствии записей за выбранный период SQL-агрегация `SUM(duration_seconds)` возвращала `None`, что вызывало `TypeError` при попытке деления на 3600. | Добавлена явная проверка `r["duration_seconds"] or 0`. При пустом результате возвращаются безопасные дефолты: `total_seconds = 0`, `total_formatted = "00:00:00"`, а на фронтенде активируется наглядный блок Empty State. |
| **5** | **Парсинг ISO-дат с суффиксом Z / UTC** | Встроенный `datetime.fromisoformat` на некоторых версиях Python не распознавал строковый суффикс `Z`, а сравнение naive и aware объектов вызывало исключение. | Написана функция `parse_iso_datetime()`, которая заменяет `Z` на `+00:00` и явно выставляет часовой пояс `timezone.utc`. |

### Детальное описание ключевых проверок

#### 1. Проверка повторного запуска таймера
- **Тест**: `test_start_timer_duplicate_prevented` в `tests/test_app.py`.
- **Сценарий**:
  1. Регистрируется сотрудник.
  2. Запускается таймер для первой задачи (например: *«Настройка CI/CD»*).
  3. Не останавливая первый таймер, отправляется второй запрос на запуск таймера для того же сотрудника (например: *«Вторая задача»*).
  4. **Ожидаемый результат**: Сервер возвращает статус `400 Bad Request`, в теле ответа содержится сообщение:
     > `У сотрудника 'Дмитрий Орлов' уже запущен таймер для задачи: «Настройка CI/CD пайплайна». Завершите текущую задачу перед запуском новой.`
  5. В базе данных остаётся ровно один активный таймер. В веб-интерфейсе отображается красный toast с ошибкой.

#### 2. Проверка сценария пустого отчёта
- **Тест**: `test_empty_report_scenario` в `tests/test_app.py`.
- **Сценарий**:
  1. Запрашивается отчёт за заведомо пустой временной диапазон (например, будущие даты `2099-01-01` — `2099-01-31`).
  2. **Ожидаемый результат**:
     - HTTP-статус `200 OK` (сервер не падает с ошибкой 500).
     - Поле `total_seconds` равно `0`.
     - Поле `total_formatted` равно `"00:00:00"`.
     - Поле `total_tasks_count` равно `0`.
     - Массивы `summary_by_employee` и `entries` пустые `[]`.
  3. В веб-интерфейсе вместо сломанной таблицы отображается красивый блок **Empty State**:
     > *📭 «Нет данных за выбранный период. За указанный временной интервал завершённых записей рабочего времени не найдено.»*

#### 3. Проверка сохранения данных после перезапуска
- **Тест**: `test_persistence_across_connection_close` в `tests/test_app.py`.
- **Сценарий**:
  1. Создаётся сотрудник и запускается таймер в первом соединении с БД.
  2. Соединение полностью закрывается (симуляция остановки сервера).
  3. Создаётся новое соединение к тому же файлу базы данных SQLite.
  4. **Ожидаемый результат**: Все данные (сотрудник, его статус, описание активной задачи) сохранены в неизменном виде.

## 📖 Интерактивная документация API

После запуска приложения доступны интерактивные спецификации:
- **Swagger UI**: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)
- **ReDoc**: [http://127.0.0.1:8000/redoc](http://127.0.0.1:8000/redoc)

### Основные эндпоинты:
- `GET /` — Главная страница дашборда (HTML).
- `GET /api/employees` — Список сотрудников с текущим статусом и активным таймером.
- `POST /api/employees` — Добавление нового сотрудника.
- `POST /api/timers/start` — Запуск таймера задачи (блокирует повторный запуск).
- `POST /api/timers/stop` — Остановка таймера и фиксация отработанного времени.
- `GET /api/timers/active` — Список всех запущенных таймеров в системе.
- `GET /api/reports` — Сводный и детальный отчёт за период с фильтрацией по датам и сотрудникам.
